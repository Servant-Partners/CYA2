# Financial import safety

Donation and accounting uploads are replacement operations, not append-only imports. The replacement window starts at the earliest accepted incoming date and extends forward. Earlier donations/accounting rows remain. Use complete exports for the intended replacement window.

## Donation frequency publication follow-up

Frequency is classified per chronological gift pattern within each donor/fund, not by applying a donor's latest pattern to all gifts. Distinct same-date/split gifts remain distinct. Two gifts in the same month or years apart are both Sporadic; regular Monthly/Quarterly/Yearly pairs can establish a new pattern and revise the preceding boundary. Established Monthly persistence retains the date-relative twelve-month context, <=25% missed-month tolerance, and amount-based catch-up/prepayment using monthly totals. Combined-fund summaries show the common per-fund frequency when funds agree, otherwise Mixed; Mixed is never assigned to a gift. See `DONATION_FREQUENCY.md` for the full contract.

Before replacement, capture the earliest changed date for every deleted/incoming donor/fund. Publication probes only each affected group's unchanged prefix (4, 13, then 26 months) for a proven Monthly checkpoint, replaying its full preceding twelve-month context. Without proof, replay only that affected group from its beginning. Group descriptors, history, and changed updates are paged/batched (64/500/500); one pending gift survives page boundaries. The rolling gift queue retains one group's twelve-month context and can grow with gift density; this is not a fixed RAM limit. Readers close before staging on the same connection. No all-affected history/change lists or per-gift full-history classification remain on standard publication.

Frequency staging/count checks and final joined updates remain inside the existing backup/delete/insert/contact/audit transaction. Evidence, validation-before-publication, locks, snapshots, rollback/commit reconciliation, authorization, exact intern-source identity, invalidation, and precaching schedules are unchanged. No schema change or database initialization was required. Synthetic regression/build results do not establish MySQL execution, rollback, working-set, or user UI acceptance; those checks remain operator-run.

## Donation reimplementation checkpoint

Account association follow-up: initial schema defines invoker-security `NormalDonationAccountMappings` and `DonationAccountAssociations` views. Financial reads require a resolved AccountId. Normal Fund designations configured for multiple accounts are unresolved; primary/merged/separate allocation semantics retain the source Fund. Nonblank intern IDs resolve only to the exact intern account, never a matching normal Fund. Upload previews show informational unresolved normal/intern canonical counts against current configuration. Account CRUD and rollback do not rewrite association foreign keys in gifts: associations follow current configuration, so deletion hides retained rows and recreation reveals them.

Existing databases need operator-approved creation of these two views before running the changed reader/preview path. The application does not create them at runtime; rerunning CREATE TABLE IF NOT EXISTS does not upgrade existing table definitions. Prepared disposable-provider association tests remain user-run, not claimed as passed. No initialized database was changed during this follow-up.

The standard donation processor now uses strict source-ID normalization, requires the Tribute System Record ID header (blank recipient cells allowed), and does not invoke name-fallback reconciliation. Standard previews validate the complete workbook and show the replacement boundary; both UI and API require explicit acknowledgment when it is more than 380 days old. Anonymous rows retain applicable source IDs without contributing donor labels or contacts.

DonationData.SourceEvidenceJson contains sanitized donation-linked observations. Replacement rebuilds affected contacts from surviving direct evidence: later blanks fall back to earlier observations and deleted suppliers stop contributing. InternSourceId and evidence are included in complete backups/rollback. A generated Docker MySQL test verifies publication, contact fallback, and rollback with restricted runtime credentials. No application database was changed.

This is an intermediate implementation, not deployment approval. The older descriptions below of name promotion and blank-clears-contact behavior are superseded on standard donation publication. Intern account administration and source-ID read/cache paths are now connected; see INTERN_ACCOUNT_BEHAVIOR.md in src/Cya2.Web/docs. Account deletion never modifies monetary records or evidence. Existing initialized databases have not been aligned and cannot reconstruct historical evidence from donor projections; explicit operator-approved schema alignment and source reload are required. Full legacy MySQL acceptance tests and coordinated resource admission remain pending. Same-day conflicting addresses currently reject publication atomically rather than silently selecting a value. The user will perform Docker/rollback simulations; interrupted runs are not claimed as passing.

## Publication contract

Admission/cancellation follow-up: validation slots now include semantic workbook parsing. The volatile background queue admits at most two active-plus-pending workbooks and 10,240,000 retained workbook bytes; it rejects overload immediately rather than retaining blocked submissions. Preview count/byte budgets remain reserved during submission and a rejected admission leaves the preview available until expiry. Owned access enforces the 15-minute lifetime; confirmation dismissal discards an unsubmitted owned preview. Preview and publication use the registered workbook reader. The obsolete private donation parser has been removed.

Cancel is separate from Close and requires current administrator authorization plus job ownership. Queued/active jobs receive cancellation tokens; a cancellation request is not proof of rollback. Commit acknowledgment and unknown-outcome reconciliation remain non-cancellable. Shutdown drains pending jobs and releases admission budgets. These are volatile, single-process controls, not durable scheduling or a bound on XLSX decompressed memory. Provider cancellation/rollback checks remain user-run.

The operator reported total upload time improving from 6:54 to 35 seconds after contact batching (contact projection/staging approximately two seconds). This is an operator-observed result, not a new profiler measurement or completed rollback acceptance.

Projected current contacts are staged using parameterized multi-row inserts within the existing publication transaction, capped at 250 rows and a conservative 256 KiB estimated command/escaped UTF-8 payload per batch. Batches span donors and the final partial batch is flushed before reconciliation. Cancellation and inserted-row count checks fail the transaction rather than publishing partial contacts. Contact selection rules are unchanged. Diagnostic logs retain only counts and phase timings. The measured pre-batching baseline was 10,437 commands taking 393,548 ms in staging; post-change database timing and rollback verification remain operator-run acceptance checks.

1. Parse the entire workbook and reject the whole upload if any populated row is invalid. Empty workbooks do not replace data. Known donation duplicates are consolidated before persistence.
   A row is skipped only when every cell is blank. Prior donation frequency history and incoming gifts use the same donor identity plus fund, not source/display names.
2. Acquire the shared financial-write gate. Donation/accounting processors, rollback and recategorization share the in-process gate. A connection-owned MySQL advisory lock also serializes persistent publication, rollback and recategorization across sessions. This is not a distributed cache-coherence or multi-worker guarantee.
3. Populate connection-local temporary staging tables before starting the persistent transaction. Runtime credentials need temporary-table rights, not persistent schema-management rights. No staging TRUNCATE, local-infile loader, live row fallback or automatic publication retry is used.
4. In one InnoDB transaction, create backup metadata/payload, delete the overlapping live range, publish staged rows and reconcile current donor contacts. Verify published counts before commit. Failures before commit roll back these persistent changes together.
5. Invalidate donation and donor-contact generations after a committed donation replacement; invalidate accounting after a committed accounting replacement. Uncertain outcomes conservatively invalidate the affected domains too. Existing summary/overview rebuild scheduling remains unchanged.

The database default must be `utf8mb4` / `utf8mb4_0900_ai_ci`: temporary donation staging depends on the database default, while some expressions use explicit `utf8mb4` collations. An incompatible default can cause MySQL error 1253. A database default change does not convert existing tables or prove that a failed import made no changes; reconcile the outcome before retrying. See [database setup](../database/README.md#initial-setup) and [Azure troubleshooting](AZURE_SETUP.md#12-troubleshooting).

Donation snapshots cover all donations and donor/contact projections because global identity resolution can relink retained gifts outside the replacement window. Rollback restores that complete state. Accounting snapshots cover all existing accounting rows. Both retain the latest unpinned snapshot and all pinned snapshots, with matching payload. Pinned snapshots currently require operational retention review; they are not automatically expired.

Contact reconciliation is current-state only: direct gifts in the upload replace the resolved donor's contact set; soft-credit-only uploads preserve verified direct contacts. New contact values receive DateCreated with DateModified null. Retained values preserve DateCreated; DateModified is set only when the exact stored ContactValue changes, including casing-only display changes with the same normalized identity. Unchanged values preserve DateModified, including null. Removed values are deleted, and an empty direct contact set clears that donor's contacts. Identity promotion preserves transferred contact timestamps; ambiguous soft-credit-only name identities do not receive constituent-specific contacts. Rollback restores snapshot values and both timestamps.

The evolving `database/schema/001_InitialSchema.sql` defines snapshot timestamp microsecond precision and the shared donor schema. Publication assigns a strictly increasing timestamp under the write lock. Existing development databases require explicit recreation using the updated initial schema and a fresh upload; the application does not automatically convert an existing per-fund schema or record a new migration for this change.

## Constituent identity

Donation workbooks must contain `Constituent ID` and `Soft Credit Recipient ID`; blank cells are accepted. IDs are opaque text (maximum 255 characters), preserving leading zeros. `DonationData.ConstituentId` retains the source ID, `DonationData.SoftCreditRecipientId` retains the recipient ID, and `Donors.ConstituentId` identifies the resolved credited donor. DonorContacts references that shared donor through DonorId rather than duplicating constituent IDs. Workbook exports must preserve IDs as text so spreadsheet numeric conversion does not discard leading zeros.

Direct non-anonymous gifts use their constituent ID. When a soft-credit recipient is shown as giving via a third party, a nonblank recipient ID identifies that donor; the intermediary's constituent ID and contacts are never used as the recipient's identity or contacts. At the user's decision, equal direct and recipient IDs identify the same person across funds. Confirm this shared namespace with the source provider before real data; equal values from unrelated namespaces would merge different people. When the applicable recipient ID is blank, existing normalized-name matching remains: a name maps to an ID only when existing and incoming identified gifts establish exactly one ID for that name. Multiple IDs keep the name-only donor separate. Existing gift evidence is considered even when its range is replaced. Anonymous gifts do not contribute identity evidence. Name-only matches cannot distinguish unrelated people with identical normalized names.

Donors are global display projections across funds, while each gift retains its fund and intern scope. A direct upload replaces the donor's current contact set, including clearing missing values. A soft-credit-only upload preserves existing direct contacts. New identity evidence can relink retained name-only gifts; later ambiguous evidence separates those gifts again. These changes and their backups publish atomically. No third-party contact values are imported for credited donors. Intern accounts remain matched by `InternName` and are unchanged by this recipient-ID field.

The new live and rollback columns are defined only in the initial schema. Previously initialized databases are not automatically changed: before deploying this version, explicitly align or recreate each disposable test database and confirm both `DonationData` and `DonationDataBackup` have the new column. Preserve any data that is no longer disposable. A new complete-format workbook is required even if every recipient ID is blank.

## Cancellation and uncertain commits

Cancellation is honored while waiting, parsing, staging and preparing the transaction. Once commit starts, caller cancellation does not interrupt acknowledgement. If acknowledgement fails, a separate connection checks the unique snapshot marker. A visible marker confirms publication; otherwise the app reports that the outcome could not be confirmed, invalidates affected caches and requires reconciliation. It never automatically retries publication.

For an uncertain result, do not immediately re-upload. Check correlated audit events, the latest snapshot and application-visible amounts/contact projections, confirm database connectivity and reconcile whether publication occurred. Rollback only after confirming the intended snapshot. Required success audit is part of the publication transaction; cache rebuilding and progress delivery remain separate post-commit work. An application/process failure can interrupt notifications; verify displayed data after reconnecting. The in-memory work queue is not durable across restarts. Saved starts use the progress ID as OperationId; prior-host unfinished starts are flagged for reconciliation, never replayed. See [audit operations](AUDIT_OPERATIONS.md).

Committed imports carry `PublicationCommitted` and separate `Warnings`. Cache/progress exceptions produce warnings rather than changing the publication outcome; terminal audit delivery cannot relabel a committed upload as failed. Cache-refresh warnings require a reload and verification, not an automatic re-upload. If progress delivery itself fails, the progress display may remain incomplete even though publication committed.

Rollback uses non-cancellable commit acknowledgement and verifies the selected snapshot's transactionally committed `Pinned` marker after an acknowledgement failure. An inconclusive result sets `OutcomeUnknown` and requires reconciliation before retrying. Combined rollback stops after an unknown or cancelled donation outcome; otherwise it preserves `ChangesCommitted` even when accounting fails or is cancelled. Each successful phase includes a transactional audit event; aggregate outcome distinguishes Partial and Unknown. Successful, partial and uncertain changes all request cache invalidation. Admin displays partial-commit notices and notification warnings. Combined rollback is still two transactions, not an atomic two-domain operation.

## Validation and remaining acceptance

The ordinary test suite exercises actual workbook processors with synthetic in-memory workbooks and fake persistence: invalid/empty rejection, valid publication, cancellation, affected-domain invalidation and cross-processor serialization. Opt-in Docker tests exercise initial schema setup, restricted runtime permissions, SQL failure rollback against existing data, prior-history donor contact recovery, accounting rollback and cancelled replacement. See [database tests](DATABASE_TESTS.md).

Enabled disposable MySQL runs cover contact timestamp preservation, identity promotion, ambiguity isolation and full snapshot rollback. Additional private-environment acceptance includes forced disconnect during commit, concurrent imports/rollback from separate app processes, large real-format exports, warm-cache UI contact checks and shutdown/reconnect behavior. This change does not resolve general exception privacy, durable queueing or other [production review](PRODUCTION_REVIEW.md) items.
